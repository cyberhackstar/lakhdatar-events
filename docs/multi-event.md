# Multi-event platform

## Ownership model

```text
Neelastack (platform) -> Organizer (Lakhdatar Events today) -> Event -> Ticket types -> Orders -> Payments -> Tickets -> Check-in
```

The pre-existing schema already separated organizers, venues, events and ticket types, and the checkout already rejected ticket types from another event.
The catalogue layer sits on top of the existing booking, payment, refund and check-in core. Later releases add explicit event-manager assignment, complimentary issuance provenance, cancellation-refund recovery and rich event administration.

## Single-event assumptions found and removed

| Where | Before | Now |
|---|---|---|
| Frontend routes | `/` redirected to `events/<defaultEventSlug>` | `/` is the multi-event home; `/events` browses; `/events/:slug` is the detail page |
| Environment files | `defaultEventSlug` | removed |
| Event page | fallback to a default slug; hard-coded "Lakhdatar Events" title | slug required; titles and branding come from the API |
| Checkout, ticket, login, staff, admin | "Lakhdatar Events" hard-coded | organizer name from event data, or Neelastack platform text |
| Admin event creation | hard-coded organizer slug, logo, colours, city | organizer resolved server-side from the actor's membership (or explicit slug); never guessed |
| Ticket fallbacks | "Lakhdatar Events", "Jaipur, Rajasthan" | neutral fallbacks |
| Production build | `angular.json` had no `fileReplacements`, so the prod bundle used the dev API URL | `environment.prod.ts` is now used |
| Deploy config | `events.lakhdatar.com`, port 4201, `/opt` | `events.neelastack.com`, port 4002, `/home/ubuntu/apps/lakhdatar-events` |

`BootstrapData` still seeds a demo Lakhdatar organizer and event, but only when `BOOTSTRAP_ENABLED=true`; it is off by default.

## Data model additions (V10)

`organizers`: logo, description, address, support hours, social links, terms.
`venues`: state, country, map URL.
`events`: short description, category, timezone, cover image, gallery, highlights, booking window, published-at, terms, refund policy, age restriction, featured, display order.
Statuses: `DRAFT, PUBLISHED, UNPUBLISHED, CANCELLED, COMPLETED, ARCHIVED`. `SOLD_OUT` is intentionally not stored; it is derived from ticket inventory.
Gallery and highlights are stored as newline-separated text and exposed as arrays.

## Lifecycle (admin API)

`POST /admin/events` create (DRAFT) · `PUT /admin/events/{id}` update · `POST .../publish` · `.../unpublish` · `.../cancel` · `.../complete` · `.../archive` ·
`POST .../ticket-types` · `PUT /admin/ticket-types/{id}` (row-locked; quantity cannot drop below reserved+sold).
Every operation checks the actor's role plus organizer/event scope. `EVENT_MANAGER` users must be explicitly assigned to an event and cannot gain access through organizer membership. They can operate their assigned event-day flows and issue complimentary tickets only for assigned events; financial refunds remain restricted to platform administrators and organizer owner/finance roles. Cancelling closes sales immediately and queues captured-payment refunds through asynchronous recovery.

## Booking window

`booking_starts_at` / `booking_ends_at` are enforced when a **new** checkout starts. An order that already holds a live reservation may still complete payment.

## SEO and SSR

Public pages (`/`, `/events`, `/events/:slug`) are server-rendered. Checkout, payment, ticket, recover, login, admin and staff are client-rendered and served with
`Cache-Control: no-store` and `X-Robots-Tag: noindex`. A missing event returns HTTP 404 from the SSR server. `robots.txt` and `sitemap.xml` are generated by the backend from the
configured public origin and list only published events.

## Not included / follow-ups

- Image upload (images are referenced by `/path` or `https://` URLs)
- Public image upload/asset management is still URL-based; the rich event editor manages the configured event metadata and ticket settings
- Prometheus and Alertmanager are not part of the Compose stack; `infra/monitoring/alerts.yml` is ready to load into yours
- Per-organizer branding beyond the existing brand configuration

## Teams, scoping and ticket delivery
- Staff and event managers belong to exactly one organizer (`organizer_members`, roles `STAFF` / `EVENT_MANAGER`, unique per user). Roles: ADMIN > ORGANIZER (owner) > EVENT_MANAGER (per event) > STAFF (per gate).
- Gate and manager assignment rejects people from another organizer (409 `DIFFERENT_ORGANIZER`); repeating an assignment is idempotent.
- Every ticket carries a signed QR credential; the ticket page receives the QR image as `qrDataUri`. Buyers get tickets by email when email is configured, and can always recover them at `/recover`.
