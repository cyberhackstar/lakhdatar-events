# Neelastack Events 2.0.32 — frontend dependency resolution hardening

## Root cause fixed
v2.0.30/v2.0.31 declared Angular framework packages at `20.3.39`. The v20 LTS Angular framework packages available from npm at release time were on the `20.3.33` line, while Angular Build had published a newer patch. npm consequently could not resolve the framework tree and reported `@angular/common@undefined` while resolving `@angular/ssr`.

## Corrected baseline
- Angular framework + SSR + CLI/build/compiler-cli: `20.3.33`
- Vitest: `3.2.7` (compatible with Angular Build 20.3.x)
- JSDOM: `29.1.1`
- TypeScript: `5.9.3`
- Node.js: `22.19.0`
- `@modelcontextprotocol/sdk`: `1.31.0` override

## Test/security architecture
- Angular official `@angular/build:unit-test` + Vitest runner retained.
- Legacy Karma/Jasmine packages are absent from the frontend manifest.
- Dependency verification fails closed if Karma or a vulnerable `braces` version appears in the generated lockfile.
- A runtime-only `npm audit --omit=dev --audit-level=high` gate is provided in addition to the complete audit.

## Installation safety
The frontend lockfile is intentionally generated by npm on a networked developer/CI host rather than fabricated offline. `npm run bootstrap:dependencies`:
1. backs up an existing lockfile,
2. regenerates it from the authoritative manifest,
3. performs a clean `npm ci`,
4. runs the enterprise dependency verifier,
5. runs the high/critical audit,
6. restores the previous lockfile if resolution fails.

No `--force` or `--legacy-peer-deps` path exists.
